# 성능 측정

측정 도구는 `frontend/perf/run.mjs`(`npm run perf`)이다. 지표와 시나리오는 `frontend/perf/README.md`에 있다.

## 절차

1. multiview-local-env로 `mock` 스택을 띄운다(5173/5180).
2. **기준선은 변경 전 코드로 잰다.** 변경 후에 재면 비교가 안 된다. 이미 바뀌었으면 `git stash`로 되돌리지 말고, 마지막 커밋을 별도 worktree에 체크아웃해 거기서 Vite를 띄워 잰다. 사용자의 작업 트리를 건드리지 않기 위해서다.
3. 측정:
   ```bash
   cd frontend && npm run perf                         # 전체, 시나리오당 20초
   npm run perf -- --only phone-scroll,phone-scroll-aggressive --seconds 30
   npm run perf -- --only phone-scroll-aggressive --break-embed A1,A2   # 실패 타일 섞인 벽
   ```
   결과 JSON은 `frontend/perf/results/`에 쌓인다.
4. **같은 시나리오를 2회 이상 재고 비교한다.** 첫 실행은 Vite 컴파일 때문에 LCP가 튄다(5초대). 차이가 작으면(±10%) 잡음으로 본다. 편차가 큰 지표(long task가 그렇다)는 회수를 늘려 σ를 같이 적고, 그래도 흔들리면 "판정 불가"로 쓴다.
5. **결과 디렉터리에는 다른 사람의 실행이 섞인다.** 구현 중인 에이전트가 돌린 것, 기준선, 네 것이 한 폴더에 쌓인다. 파일명 타임스탬프로 구간을 구분해 표에 넣은 것만 세고, 보고서에 어느 구간이 무엇인지 적는다.
6. **측정 코드를 건드렸으면 그것부터 분리 검증한다.** 러너에 계측(타이머 래핑 등)을 새로 넣은 뒤 수치가 움직였다면, 계측을 뺀 사본으로 다시 재서 계측 탓이 아님을 보이고 그 차이를 숫자로 적는다.

## 해석

| 지표 | 무엇을 뜻하나 | 주의 |
|---|---|---|
| players built | 측정 중 새로 만든 플레이어 수 | 폰에서 가장 중요. 많으면 메모리가 쌓여 iOS Safari가 탭을 죽인다 (21 → 4로 줄인 전례) |
| players (peak) | 동시에 떠 있던 수 | 폰은 예산 4(`lib/playerBudget.ts`)가 기준 |
| RSS peak | 브라우저 전체(유튜브 iframe 포함) 메모리 | Chromium만. **Windows에서는 항상 0** — `run.mjs`의 `rssMb()`가 `ps -o rss=`를 쓰고 Git Bash `ps`는 `-o`를 모른다. 이 PC에서는 메모리 판정을 `heap after GC`로만 한다 |
| heap after GC | GC 후에도 남은 페이지 JS 메모리 | 누수 판정의 기준선. 밴드 안이라도 **범위가 겹치지 않는 일정한 이동**이면 잡음이 아니다 — 원인 후보를 적고 다음 라운드에서 다시 본다 |
| playing 표본 평균 | 측정 내내 실제로 재생 중이던 타일 수의 평균 | peak만 보면 "2개까지"는 지켜지는데 대부분 1개인 상태를 놓친다. `playing=0` 표본은 재생 실패가 아니라 스크롤 중간 점프 직후일 수 있으니 `scrollY`와 함께 본다 |
| JS heap | 페이지 자체 JS 메모리 | 플레이어 churn이 크면 같이 커진다 |
| fps / worst frame | 헤드리스에서 영상 여럿이면 30fps 근처가 정상 | 절대값보다 전후 비교 |
| download | 영상 포함 받은 양 | 멈춰 둔 플레이어가 받는지 확인 |

WebKit 시나리오는 CPU·메모리가 비어 있고(도구 한계), 이 PC의 headless WebKit에는 H.264가 없어 **재생 자체가 되지 않는다** — 재생 수를 세는 판정은 Chromium 시나리오로만 한다. 실제 iPhone의 메모리 한도는 에뮬레이션되지 않으므로 "크래시가 사라졌다"고 단정하지 않는다. "플레이어 생성이 N→M으로 줄었다"처럼 잰 것만 말한다.

**기준선에 없던 구성은 전후 비교가 아니다.** `--break-embed`로 잰 수치(실패 타일이 섞인 벽)처럼 변경 전에 재지 않은 구성은 "신규 수치"로 따로 적고, 몇 배 좋아졌다고 쓰지 않는다. 임베드 실패는 mock 방송으로 재현되지 않아서 수정 전 기준선에 그 상태가 아예 없다 — 이 경우 판정은 코드 논증 + 수정 후 단독 측정 + 기기 확인(mobile-verification의 드릴 절)으로 나눠서 한다.

## 보고 형식

```markdown
## 성능 비교: {변경 요약}
| 시나리오 | 지표 | 전 | 후 | 판정 |
...
- 회귀: {있으면 무엇이, 얼마나}
- 잡음 판단 근거: {반복 측정 결과}
- 측정 못 한 것: {WebKit 메모리, 실제 기기 등}
```
판정은 개선 / 동일(±10%) / 회귀. 회귀가 있으면 원인 후보(어느 코드 변경 때문인지)를 함께 적는다.
