# 성능 측정

측정 도구는 `frontend/perf/run.mjs`(`npm run perf`)이다. 지표와 시나리오는 `frontend/perf/README.md`에 있다.

## 절차

1. multiview-local-env로 `mock` 스택을 띄운다(5173/5180).
2. **기준선은 변경 전 코드로 잰다.** 변경 후에 재면 비교가 안 된다. 이미 바뀌었으면 `git stash`로 되돌리지 말고, 마지막 커밋을 별도 worktree에 체크아웃해 거기서 Vite를 띄워 잰다. 사용자의 작업 트리를 건드리지 않기 위해서다.
3. 측정:
   ```bash
   cd frontend && npm run perf                         # 전체, 시나리오당 20초
   npm run perf -- --only phone-scroll,phone-scroll-aggressive --seconds 30
   ```
   결과 JSON은 `frontend/perf/results/`에 쌓인다.
4. **같은 시나리오를 2회 이상 재고 비교한다.** 첫 실행은 Vite 컴파일 때문에 LCP가 튄다(5초대). 차이가 작으면(±10%) 잡음으로 본다.

## 해석

| 지표 | 무엇을 뜻하나 | 주의 |
|---|---|---|
| players built | 측정 중 새로 만든 플레이어 수 | 폰에서 가장 중요. 많으면 메모리가 쌓여 iOS Safari가 탭을 죽인다 (21 → 4로 줄인 전례) |
| players (peak) | 동시에 떠 있던 수 | 폰은 예산 4(`lib/playerBudget.ts`)가 기준 |
| RSS peak | 브라우저 전체(유튜브 iframe 포함) 메모리 | Chromium만 |
| JS heap | 페이지 자체 JS 메모리 | 플레이어 churn이 크면 같이 커진다 |
| fps / worst frame | 헤드리스에서 영상 여럿이면 30fps 근처가 정상 | 절대값보다 전후 비교 |
| download | 영상 포함 받은 양 | 멈춰 둔 플레이어가 받는지 확인 |

WebKit 시나리오는 CPU·메모리가 비어 있다(도구 한계). 실제 iPhone의 메모리 한도는 에뮬레이션되지 않으므로 "크래시가 사라졌다"고 단정하지 않는다. "플레이어 생성이 N→M으로 줄었다"처럼 잰 것만 말한다.

## 보고 형식

```markdown
## 성능 비교: {변경 요약}
| 시나리오 | 지표 | 전 | 후 | 판정 |
...
- 회귀: {있으면 무엇이, 얼마나}
- 잡음 판단 근거: {반복 측정 결과}
- 측정 못 한 것: {WebKit 메모리, 실제 기기 등}
```
판정은 개선 / 동일(±10%) / 회귀. 회귀가 있으면 원인 후보(어느 코드 변경 때문인지)를 함께 적는다.
