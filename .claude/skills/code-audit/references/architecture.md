# 아키텍처 점검표

설계가 **바뀔 이유가 한 곳에 모여 있는지**, 경계가 새지 않는지를 본다.

## 백엔드
- `Program.cs`가 비대해지지 않았나: 엔드포인트 정의 외의 로직(투영, 헤더, 제한)이 서비스로 빠질 때가 됐나. 정적 로컬 함수가 테스트 불가능한 로직을 숨기고 있지 않나.
- 서비스 경계: `LivePollingService`(언제) / `YouTubeLiveClient`(어떻게 가져오나) / `LiveStreamStore`(보관) / `VenueScheduleProvider`(영업 상태). 서로의 책임을 침범하는 호출이 있나.
- 상태가 메모리에 있다(복제본 1 전제, README에 명시). 이 전제가 코드에서 깨지는 곳(파일 캐시, 정적 변수)이 있나.
- 설정: `IOptions`/`IOptionsMonitor` 사용이 일관적인가. `venues.json` 핫 리로드 시 버전·캐시 무효화가 모든 소비자에 전달되나.
- 모델 경계: API 응답 모델(`ApiResponses.cs`)과 내부 모델이 섞여 내부 필드가 새어 나가지 않나.

## 프론트엔드
- `lib/`(순수 로직, 테스트됨)과 `components/`(React)의 경계. 컴포넌트 안에 테스트 없는 판단 로직이 쌓였나(특히 `PlayerTile.tsx`: 플레이어 수명, 가시성, 예산, 슬롯, 감시).
- 전역 모듈 상태(예: `compactPlayerBudget` 같은 싱글턴)의 수명과 테스트 격리.
- `App.tsx`의 상태·효과 수: 분리할 훅이 보이나. 폴링·가시성·단축키가 한 컴포넌트에 몰려 있나.
- API 계약: `lib/types.ts`와 백엔드 응답 모델이 일치하나(필드명, null 가능성, enum 문자열).
- CSS 구조: `styles.css`의 미디어쿼리 블록 간 우선순위 의존(나중 규칙이 이기는 것에 기대는 곳), 모바일/데스크톱 분기 중복.

## 데스크톱 셸
- 웹 프론트엔드와 셸의 경계(`lib/shell.ts` ↔ Tauri 명령). 셸 전용 분기가 웹 코드 곳곳에 흩어져 있나.
- 편집기(`editor/`)와 셸 파일 쓰기(`editor.rs`)의 책임 분담.

## 테스트 가능성
- 시간·네트워크·브라우저 API 의존이 주입 가능한가(시계, `navigator`, `IntersectionObserver`).
- 테스트가 구현이 아니라 동작을 검증하나.
